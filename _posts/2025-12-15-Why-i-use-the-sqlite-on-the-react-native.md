필자는 Spring과 Mybatis를 주력으로 사용하는 3년차 개발자이고 복잡한 데이터 처리를 위해 SQL로 데이터를 풀어내는 것을 좋아해서 JPA보다는 직접 쿼리로 데이터를 처리하는 것을 선호한다.
이번에 React Native로 앱을 개발하면서 로컬 DB를 선정하는 과정에서 겪은 **WatermelonDB vs. SQLite**를 각각 적용해본 경헙을 공유하려고 한다.

## WatermelonDB: 마치 JPA의 맛을 느낀

처음에는 AsyncStorage를 사용하여 로컬 저장소를 구현하였지만 해당 방식은 모든 데이터를 문자열로 저장하고 데이터가 많을수록 데이터 처리 혹은 조회할 때 성능에 문제가 있다고 하여 현재 개발 중인 메모 어플에는 맞지 않다고 생각하여 여러 로컬 DB를 찾아보다가 RN에서 성능 좋고 유명하다고 하는 WatermelonDB를 현재 개발 중인 프로젝트에 적용하였다. 하지만 해당 기능을 적용하고 생각한 점이 간단한 어플임에도 불구하고 손에 많이 간다는 느낌이 들었다.

### Java 개발자 시선에서 본 WatermelonDB의 특징

- **JPA와의 유사:** Schema를 정의하고 Model 클래스를 만들고 여러 Annotation을 사용하여 테이블 및 데이터를 조작한다.

- **SQL 작성 X:** 기능 내부적으로는 SQL을 사용하지만 개발자가 직접 작성하지 않고 Builder 방식처럼 SQL을 제어할 수 있다.

## SQLite: 역시 이거라고 생각했다

요즘 같은 시대에 직접 SQL을 작성하고 데이터를 관리한다는 방식이 누군가에게는 구식으로 보일 수 있지만 자기가 잘하는 것을 뭐든지 최신이 좋은 것은 아니라고 생각한다. 자기가 잘하고 자신있는 것을 사용해서 최적화 한다면 그 만큼 효율성을 주는 것은 없다고 생각한다.

필자는 현재 Expo를 사용하고 있다. `expo-sqlite`를 사용하였다.

### Java 개발자 시선에서 본 SQlite의 특징

- **직관적인 제어:** 복잡한 조인이나 서브쿼리도 평소처럼 작성해서 좋다.
- **Mybatis와의 유사:** DB 인스턴스 생성하고 SQL 작성하고 Service단과 같은 로직을 작성해서 결과를 받고 그냥 스프링과 유사하다.
  - 이런 점에서 너무 맘에든다. 물론 시대를 받아들일거면 그 만큼 러닝커브가 발생하겠지만, 현재는 리엑트 네이티브도 학습하는 단계이기 때문에 데이터 처리 방식만큼은 자신있는 쪽으로 가는게 맞다고 생각하여 선택하였다.

### 장점

- **러닝 커브 제로:** 평소와 같이 개발하면 되어서 학습 단계가 존재하지 않는다.
- **유연한:** Mybatis xml 퀄 짜듯이 JS에서도 SQL을 작성하면 된다.
- **가벼움:** 무거운 Wrapping 레이어가 존재하지 않아서 어플 사이즈 줄이기 위해서도 좋다.

## 비교 요약: Java 개발자 관점

| 특징            | WatermelonDB                                 | SQLite (Direct)                               |
| :-------------- | :------------------------------------------- | :-------------------------------------------- |
| **비유**        | **JPA (Hibernate) + RxJava**                 | **MyBatis / JDBC**                            |
| **데이터 접근** | 객체 중심 (ORM)                              | 데이터 중심 (SQL)                             |
| **쿼리 작성**   | Query Builder 메서드 사용                    | **Raw SQL 작성 (MyBatis 스타일)**             |
| **생산성**      | 초기 세팅 오래 걸림, 유지보수 시 편함        | **초기 개발 매우 빠름**, 쿼리 관리 필요       |
| **장점**        | 데이터 변경 시 UI 자동 업데이트 (Observable) | **내가 짠 쿼리 그대로 동작함 (Full Control)** |

## 결론: SQL 잘 짜면 굳이 ORM???

이번에 경험하면서 WatermelonDB도 상당히 훌륭한 라이브러리라고 느꼇다. 하지만 RN도 학습하고 있는 와중에 해당 라이브러리도 학승할 순 없기도 했고 어차피 SQL도 잘 작성하고 하니깐 굳이?? 라는 생각을 했다. (그래도 잘 모르는 개발자들에게는 좋은 라이브러리라고 생각한다.)

하지만 과하면 오히려 독이 되는 법이라고 생각하는데 SQL을 작성함으로 좀 더 최적화 시킬 수 있는데 해당 라이브러리가 아무리 편하다고 해서 사용하는 것은 아닌 것 같다.

- **JPA의 영속성 컨텍스트 관리가 귀찮고 그냥 SQL 튜닝해서 박는 게 편하다?**
- **복잡한 객체 관계 매핑보다 JOIN 쿼리 한 줄이 더 깔끔하다고 느낀다?**

그렇다면 RN에서도 굳이 무거운 ORM을 쓰려고 애쓰지 말고 **Raw SQL**이라는 가장 강력한 무기가 이미 있으니깐 SQLite를 사용하는 방법도 좋은 것 같다.

> _"Simple is Best. And SQL is Simple enough for me."_
